# 온도 모니터링 시스템 (SIG-5560) — 개발 설명서

> MES 취업 포트폴리오용. "무엇을 했는지"보다 **"왜 이렇게 했는지"** 를 중심으로 정리했습니다.
> 면접에서 그대로 설명할 수 있도록 각 절 끝에 **면접 포인트**를 달아 두었습니다.

## 0. 실행 방법

1. **DB 만들기**: SSMS에서 `Database/01_CreateDatabase.sql` 을 열고 F5
   (명령줄: `sqlcmd -S localhost -E -C -f 65001 -i Database\01_CreateDatabase.sql`)
   - 여러 번 실행해도 안전합니다(이미 있으면 건너뜀). SQL Server 2016 SP1 이상.
2. **연결 문자열 확인**: `TempMonitor/App.config` 의 `TempMonitorDB` (기본: localhost, Windows 인증)
   - SQL Server Express 처럼 이름 있는 인스턴스면 `Server=localhost\SQLEXPRESS` 로 (SSMS 접속 창의 서버 이름 그대로)
3. **센서 IP 확인**: spFinder 로 SIG-5560 을 검색해 IP 확인 (포트 기본 502)
   - 장비가 없으면 `Sig5560Simulator` 프로젝트를 실행하고 IP `127.0.0.1` 로 연결 (7장 참고)
4. **(선택) 카카오톡 토큰 등록**: `Database/02_KakaoToken.ps1` 실행 (3-4 참고)
5. Visual Studio 에서 실행 → 로그인

> 카카오 키/토큰은 비밀값이라 Git 에 올리지 않고 DB(TB_CONFIG)에만 저장합니다. PC 를 옮기면 4번만 다시 하면 됩니다.

| 테스트 계정 | 비밀번호 | 권한 |
|---|---|---|
| admin | admin1234 | 관리자 (설정 변경 가능) |
| operator | oper1234 | 작업자 (조회만) |

> 비밀번호 5회 틀리면 잠깁니다. 풀기: `UPDATE TB_USER SET FAIL_CNT = 0 WHERE USER_ID = 'admin';`

## 1. 전체 구조

```
[PT100 센서] ─ [SIG-5560] ── Modbus/TCP(502) ──▶ [TempMonitor (WinForms)] ──▶ [SQL Server]
                                                        │
                                                        └──▶ 카카오톡 API (경고 알림)
```

### 1-1. 폴더/계층 구조

```
TempMonitor/
├─ Program.cs            진입점: 로그인 → 메인 → (로그아웃 시) 다시 로그인
├─ Session.cs            로그인 사용자 보관
├─ LoginForm.cs          로그인 화면 (입력/표시만)
├─ MainForm.cs           메인 화면 (입력/표시 + 흐름 제어)
├─ Comm/                 ── 통신 계층 (장비와 대화)
│   ├─ ModbusTcpClient.cs   Modbus/TCP 프로토콜 직접 구현
│   └─ Sig5560Client.cs     SIG-5560 레지스터 맵 (어느 주소에 무엇이 있는지)
├─ Services/             ── 업무 규칙 계층
│   ├─ AuthService.cs       로그인 규칙 (잠금, 실패 횟수, 이력)
│   ├─ PasswordHasher.cs    비밀번호 해시
│   └─ KakaoService.cs      카카오톡 발송 + 토큰 갱신
├─ Data/                 ── 데이터 접근 계층 (SQL 은 여기에만)
│   ├─ DbHelper.cs          연결/실행/파라미터 공통
│   └─ *Repository.cs       테이블별 조회·저장
└─ Models/               ── 계층 사이를 오가는 데이터 그릇
Database/
├─ 01_CreateDatabase.sql  DB/테이블/기초 데이터 생성 (idempotent)
└─ 02_KakaoToken.ps1      카카오 토큰 최초 발급 → TB_CONFIG 저장
Sig5560Simulator/         장비 없이 테스트하는 가상 SIG-5560 (Modbus/TCP 서버)
```

**왜 이렇게 나눴나?**
- 처음 만들 때는 버튼 클릭 이벤트 안에 SQL 과 소켓 코드를 다 넣는 게 제일 빠릅니다. 하지만
  - 센서가 다른 모델로 바뀌면? → `Sig5560Client` 만 새로 만들면 됨 (화면·DB 코드는 그대로)
  - DB 가 Oracle 로 바뀌면? → `Data/` 만 수정
  - 화면을 WPF/웹으로 바꾸면? → `Comm/ Services/ Data/` 는 그대로 재사용
- 즉 **"바뀌는 이유가 다른 코드는 다른 곳에 둔다"** (관심사 분리). MES 는 설비·DB·화면이 따로따로 바뀌는 일이 아주 흔합니다.

> **면접 포인트**: "통신 / 업무 규칙 / 데이터 접근 / 화면을 계층으로 분리했고, 장비 프로토콜(ModbusTcpClient)과 장비별 레지스터 맵(Sig5560Client)도 분리해서 센서 기종이 늘어나도 확장이 쉽도록 했습니다."

## 2. Modbus/TCP 통신 (Comm/)

라이브러리(NModbus 등)를 쓰지 않고 **직접 구현**했습니다. 설비 통신은 MES 개발자의 핵심 역량이고, 프레임을 직접 다뤄 본 경험은 면접에서 강하게 어필됩니다.

### 2-1. 사용하는 레지스터 (사용자 설명서 5장)

| 내용 | 함수코드 | 주소 | 값 해석 |
|---|---|---|---|
| 현재 온도 | 04 (Read Input Registers) | 0 | int16 ÷ 10 (272 → 27.2℃) |
| 에러 코드 | 04 | 8 | 0 정상 / 3 센서 끊김 / 4 측정 실패 … |
| 최저 온도 | 04 | 16 | int16 ÷ 10 (0xFFB9 = -71 → -7.1℃) |
| 최고 온도 | 04 | 32 | int16 ÷ 10 |
| 최저/최고 초기화 | 05 (Write Single Coil) | 160 | 0xFF00 쓰면 초기화 |

### 2-2. 실제 프레임 예시 — 온도 읽기

```
요청 (PC → 센서) 12바이트
00 01 | 00 00 | 00 06 | 01 | 04 | 00 00 | 00 21
 TID    PID     길이   UID   FC  시작주소  개수(33)

응답 (센서 → PC)
00 01 | 00 00 | 00 45 | 01 | 04 | 42 | 01 10 ... 
 TID 같음               UID  FC  바이트수 0x0110 = 272 → 27.2℃
```

### 2-3. 구현 포인트와 이유

| 구현 | 이유 |
|---|---|
| **0~32번을 한 번에 읽기** (33개) | 4번 왕복 → 1번 왕복. 통신 횟수가 줄어 빠르고 장비 부담도 적음. 장비가 빈 주소를 거부(예외코드 2)하면 자동으로 개별 읽기로 전환 |
| **`ReadExactAsync`** (원하는 바이트 수가 찰 때까지 반복 읽기) | TCP 는 "스트림"이라 한 번 `Read` 에 응답 전체가 온다는 보장이 없음. 초보자가 가장 많이 틀리는 부분 |
| **Transaction ID 검사** | 늦게 도착한 이전 응답을 현재 응답으로 착각하는 것 방지 |
| **예외 응답 처리** (FC 최상위 비트 0x80) | 장비가 "그 주소 없음" 등을 알려줄 때 원인을 메시지로 보여줌 |
| **연결/응답 타임아웃** (3초) | `TcpClient.ConnectAsync` 는 기본 타임아웃이 약 20초라 화면이 오래 멈춘 것처럼 보임 |
| **오류 시 소켓을 끊음** | 응답이 반쯤 남은 소켓을 계속 쓰면 다음 응답이 엉망이 됨 → 끊고 재연결이 안전 |
| **`SemaphoreSlim` 잠금** | 폴링 중에 사용자가 '초기화' 버튼을 누르면 요청 2개가 동시에 나가 응답이 섞일 수 있음. 한 번에 한 요청만 |
| **int16(부호 있음)으로 변환** | 영하 온도는 2의 보수로 옴 (0xFFB9 → -71). `ushort` 로 읽으면 65465 가 되어버림 |
| **`decimal` 로 ÷10** | `double` 27.2 는 실제로 27.19999… 이 될 수 있음. 정확한 소수 1자리가 필요 |

> **면접 포인트**: "Modbus TCP 의 MBAP 헤더(TID/PID/Length/UnitID)와 PDU 를 직접 조립했고, TCP 스트림 특성 때문에 길이만큼 반복 수신, Transaction ID 검증, 예외 응답(0x80) 처리, 타임아웃 후 재연결까지 구현했습니다."

## 3. 주요 기능별 흐름

### 3-1. 로그인 (`LoginForm` → `AuthService` → `UserRepository`)

```
아이디/비번 입력 → DB 에서 SALT·HASH 조회 → SHA256(SALT+입력비번) 비교
  ├ 계정 없음 / 비번 틀림 → 같은 메시지 ("아이디 또는 비밀번호가 올바르지 않습니다")
  ├ 5회 연속 실패 → 잠금
  └ 성공 → FAIL_CNT=0, LAST_LOGIN_DT 갱신, Session 에 사용자 저장
모든 시도는 TB_LOGIN_HIST 에 기록
```

| 결정 | 이유 |
|---|---|
| 비밀번호를 해시로만 저장 | DB 가 유출돼도 원래 비밀번호를 알 수 없게 |
| 사용자마다 다른 SALT | 같은 비밀번호라도 해시가 달라져, 미리 계산된 해시표(레인보우 테이블) 공격 무력화 |
| 계정 없음/비번 틀림 메시지 동일 | 메시지가 다르면 "이 아이디는 존재함"을 공격자에게 알려줌 |
| 고정 시간 비교 (`PasswordHasher.Verify`) | 첫 바이트부터 다르면 바로 리턴하는 비교는 응답 시간 차이로 정보가 샘 |
| 로그인 이력 테이블 | MES 는 "누가 언제 접속해 무엇을 바꿨나" 추적(감사)이 필수 |

> 한계(면접에서 먼저 말하면 좋음): 학습용으로 SHA-256 을 썼지만 실무에서는 일부러 느린 **PBKDF2/bcrypt** 를 써야 합니다.

### 3-2. 실시간 모니터링 (폴링 루프)

```
[연결] 클릭
  └ PollLoopAsync (반복)
       ├ 끊겼으면 자동 재연결
       ├ 센서 읽기 (FC04)
       ├ 상태 판정:  에러코드≠0 → ERROR / 온도 ≥ 기준 → WARNING / 그 외 NORMAL
       ├ 화면 갱신: 현재온도, 램프 색, 최저/최고, 실시간 그리드, 차트
       ├ 경고 판단 → 경고 기록 / 카톡
       ├ DB 저장 판단
       └ 읽기 주기만큼 대기 (실패 중이면 최소 3초)
```

**왜 `Timer` 가 아니라 `async` 루프인가?**
- `Timer` 는 1초마다 무조건 실행됩니다. 센서 응답이 2초 걸리면 요청이 겹칩니다.
- `async` 루프는 "읽기 끝 → 대기 → 다음 읽기"라 절대 겹치지 않습니다.
- UI 스레드에서 시작한 `await` 는 끝나면 UI 스레드로 돌아오므로 `Invoke` 없이 화면을 바로 고칠 수 있고, 기다리는 동안 화면은 멈추지 않습니다.

**자동 재연결**: 공장은 케이블 흔들림·스위치 재부팅으로 순간 끊김이 흔합니다. 사람이 다시 [연결]을 누를 때까지 데이터가 비면 안 되므로 루프가 스스로 재연결합니다.

### 3-3. DB 저장 주기

- 읽기 1초 / 저장 5초 (설정 가능). 1초마다 저장하면 하루 86,400건 → 5초면 17,280건.
- **단, 상태가 바뀌는 순간(정상→경고, 경고→정상, 오류)은 주기와 상관없이 즉시 저장**합니다. 경고가 발생한 정확한 시각을 놓치면 안 되기 때문입니다.
- 저장 주기 < 읽기 주기 설정은 막습니다 (읽지 않은 값을 저장할 수는 없음).
- DB 저장에 실패해도 모니터링은 계속됩니다 (상태바에 표시).

### 3-4. 경고 & 카카오톡

경고는 **"구간"** 단위로 관리합니다. 정상 → 경고 시작 ~ 정상 복귀까지가 경고 1건입니다.

```
29.9 → 30.1  ① [온도 경고]  현재 30.1℃ (기준 30.0℃ 이상)
     → 35.2  ② [온도 상승]  직전 알림 30.1℃ 대비 +5.1℃        ← 최소 간격 무시, 즉시
     (10분)  ③ [경고 지속]  지속 10분 / 최고 40.6℃            ← 알림 최소 간격마다
     → 28.9  ④ [정상 복귀]  경고 지속 12분 / 최고 40.6℃ (시각)
```

| 규칙 | 이유 |
|---|---|
| ① 정상→경고 **바뀌는 순간** 경고 1건 기록 | 매초 기록하면 1시간 고온에 3,600건 |
| ② 직전 알림보다 **재알림 상승 폭(기본 5℃)** 이상 오르면 간격 무시하고 즉시 | 30℃ 에서 알린 뒤 10분 동안 40℃ 까지 올라도 모르는 문제 해결. 악화는 놓치지 않기 |
| ③ 경고가 계속되면 "알림 최소 간격"마다 재기록 | "계속 고온이었다"는 사실은 남겨야 함 |
| ④ 복귀 시 구간 요약(지속 시간, 최고 온도) | 언제 끝났고 최악이 몇 도였는지 → 대응 결과 확인 |
| ①③ 카톡은 마지막 발송 후 최소 간격이 지나야 발송 | 기준 온도 근처에서 29.9 ↔ 30.1 을 오가면 카톡 폭탄 |
| ④ 는 그 구간에 카톡을 실제로 보냈을 때만 | 시작을 안 알렸는데 복귀만 오는 혼란 방지 (오르락내리락 시 간격당 최대 2건) |
| 센서 오류(ERROR)는 구간을 끝내지 않음 | 일시적 오류 때문에 복귀 알림이 잘못 나가지 않게 |
| 카톡 발송은 **기다리지 않음** (fire-and-forget) | 카카오 응답이 늦어도(최대 10초) 센서 읽기/화면 갱신이 멈추면 안 됨 |
| 발송 실패해도 시도 시각은 기록 | 카카오 서버 장애 시 매초 재시도 방지 |
| 경고 기록 시 **그때의 기준 온도**도 저장 | 나중에 기준을 바꿔도 "왜 경고였는지" 설명 가능 |
| 카톡 결과(발송/실패/생략/미사용)를 경고에 기록 | "경고는 났는데 왜 카톡이 안 왔지?" 에 답할 수 있음 |

> **면접 포인트**: "알림을 이벤트(구간) 생명주기로 관리했습니다. 간격 제한으로 알림 피로를 줄이면서, 변화량 기준 재알림과 복귀 요약으로 중요한 변화는 놓치지 않게 했습니다. SCADA/MES 알람 관리의 발생(Active)-해제(Clear) 개념과 같습니다."

REST API 키 → 클라이언트 시크릿 → 브라우저 동의 → 주소창(`https://localhost/?code=...`) 붙여넣기 → TB_CONFIG 에 저장.
그 다음 [카톡 발송 내역] 탭 → [테스트 발송].

- 액세스 토큰(약 6시간)이 만료되면 401 응답 → 리프레시 토큰(약 60일)으로 새 토큰을 받아 DB 에 저장하고 한 번 더 보냅니다. 새로 만든 앱은 클라이언트 시크릿이 기본 ON 이라 갱신 요청에도 `client_secret` 을 함께 보냅니다.
- "나에게 보내기" 는 무료지만 **나와의 채팅이라 푸시 알림이 오지 않습니다.** 실무에서는 알림톡(유료) + SMS 대체 발송을 씁니다. 발송 로직이 `KakaoService` 한 곳에 있어 수단만 바꾸면 됩니다.

### 3-5. 조회 탭 (온도 기록 / 경고 내역 / 카톡 발송 내역)

- **반열린 구간** `시작 <= 시각 < 끝` 으로 조회. `BETWEEN` 은 양끝 포함이라 15:00:00 데이터가 "14~15시"와 "15~16시" 조회에 둘 다 나옵니다.
- 날짜만 고르는 카톡 탭은 `종료일 다음날 0시 미만` 으로 조회해서 종료일 하루 전체를 포함.
- 온도 기록은 최대 50,000건 (`TOP`). 1년치를 한 번에 그리드에 올리면 프로그램이 멈춥니다.
- 조회 중 버튼 비활성화 → 중복 클릭 방지.
- **종료 시각 "지금 따라가기"**: 프로그램을 켜 둔 채 시간이 지나면 종료 시각이 켠 시각에 멈춰 새 데이터가 안 보이는 문제가 있었음 → 종료가 현재 분 이후면 조회/탭 이동 때 현재 시각으로 갱신, 과거 시각을 직접 고르면 고정.
- 온도 기록의 센서 오류 행은 공통코드(SENSOR_ERROR)를 한 번 더 JOIN 해서 `센서 오류 (온도센서 연결 끊김)` 처럼 **오류 종류까지** 표시. 원시 코드(ERROR_CD)를 저장해 두었기 때문에 과거 데이터에도 소급 적용됨.
- **보기 전용 그리드** (`MakeViewOnly`): 행 선택 하이라이트 제거(경고/오류 색이 가려지지 않게), 편집 불가.
  정렬은 의미 있는 컬럼만 허용 — 실시간: 없음(최신이 항상 맨 위) / 온도 기록: 시간·온도·상태 / 경고·카톡: 시각만.
  조회 직후 시각 컬럼에 ▼ 표시(쿼리가 시각 DESC), 정렬 가능한 헤더는 손 모양 커서 + 툴팁.

### 3-5-1. 데이터 출처

| 화면 | 출처 |
|---|---|
| 실시간 온도 탭 (현재 온도, 차트, 실시간 기록) | 센서 → **메모리** (DB 를 거치지 않아 빠르고, DB 장애와 무관하게 동작) |
| 온도 기록 / 경고 내역 / 카톡 발송 내역 / 설정 | **DB** 조회 |

실시간 기록은 읽을 때마다(1초), 온도 기록은 저장할 때마다(5초 + 상태 변화) 쌓이므로 건수가 다른 것이 정상입니다.

### 3-6. 설정 / 권한

- 설정 탭은 관리자만 활성화. **그리고 저장 버튼 처리 코드에서도 권한을 한 번 더 확인**합니다 (화면만 막는 것은 보안이 아님).
- 여러 설정을 **트랜잭션 1개**로 저장 → 중간에 실패하면 전부 롤백 (설정이 반만 바뀐 상태 방지).
- 누가 언제 바꿨는지 `UPD_USER_ID`, `UPD_DT` 기록.

## 4. DB 설계

### 4-1. ERD

```
TB_USER (1) ─ 로그인 이력은 FK 없음 ─ TB_LOGIN_HIST (N)

TB_SENSOR (1) ──< TB_TEMP_LOG (N)
     │
     └────────< TB_ALERT_LOG (1) ──< TB_KAKAO_LOG (N, ALERT_ID NULL 허용)

TB_COMMON_CODE  : 상태/권한 등 코드 → 이름  (조회 시 JOIN)
TB_CONFIG       : 환경설정 Key-Value
```

### 4-2. 테이블별 설계 이유

| 테이블 | 역할 | 핵심 설계 이유 |
|---|---|---|
| **TB_COMMON_CODE** | 코드-이름 사전 | 데이터엔 `WARNING` 같은 코드만 저장, 화면 이름(경고)은 JOIN. 이름이 바뀌어도 수백만 건 데이터를 고칠 필요 없음. **MES 에서 거의 100% 쓰는 패턴** |
| **TB_USER** | 사용자 | PK=USER_ID(자연키), 해시/솔트, 권한 CHECK 제약, 실패 횟수 |
| **TB_LOGIN_HIST** | 접속 감사 로그 | 없는 아이디로 시도한 것도 남겨야 하므로 FK 를 일부러 안 검 |
| **TB_SENSOR** | 설비 마스터 | 지금은 1대지만 측정 데이터에 SENSOR_ID 를 붙여 두면 10대가 돼도 구조 변경 없음 |
| **TB_TEMP_LOG** | 측정 이력 (가장 큼) | 아래 4-3 참조 |
| **TB_ALERT_LOG** | 경고 이력 | 그 시점 기준 온도(THRESHOLD_VALUE) 스냅샷 저장 |
| **TB_KAKAO_LOG** | 발송 이력 | 경고 1 : 발송 N. 테스트 발송은 경고와 무관해서 ALERT_ID NULL 허용. 실패 사유 저장 |
| **TB_CONFIG** | 설정 | Key-Value → 항목이 늘어도 ALTER TABLE 없이 행만 추가. (단점: 형 변환·검증을 코드에서 해야 함 → `AppConfig` 클래스 한 곳에서 처리) |

### 4-3. TB_TEMP_LOG 를 자세히

```sql
LOG_ID      BIGINT IDENTITY  -- 클러스터드 PK
SENSOR_ID   INT              -- FK
MEASURE_DT  DATETIME2(0)     -- 센서에서 읽은 시각
TEMP_VALUE  DECIMAL(5,1) NULL
STATUS_CD   VARCHAR(10)      -- NORMAL/WARNING/ERROR (CHECK 제약)
ERROR_CD    TINYINT
REG_DT      DATETIME2(3)     -- DB 에 들어간 시각
+ 인덱스 IX_TB_TEMP_LOG_SENSOR_DT (SENSOR_ID, MEASURE_DT) INCLUDE (TEMP_VALUE, STATUS_CD, ERROR_CD)
```

| 선택 | 이유 |
|---|---|
| `BIGINT` | INT 최대 21억. 센서 10대 × 1초 저장이면 약 7년이면 넘음. MES 이력 테이블은 BIGINT 가 기본 |
| `DECIMAL(5,1)` (FLOAT 아님) | 센서 해상도가 0.1℃ → 소수 1자리 고정이 정확. FLOAT 은 오차로 `= 27.2` 비교가 실패할 수 있음. 범위 -200.0~850.0 은 5자리로 충분 |
| `TEMP_VALUE NULL` 허용 | 센서 오류 시 값을 0 으로 넣으면 "진짜 0℃"와 구분 불가 → NULL = "모름" |
| `DATETIME2(0)` (DATETIME 아님) | 초 단위면 충분, 6바이트로 DATETIME(8바이트)보다 작고 정밀도 오차(3.33ms 반올림)도 없음 |
| `MEASURE_DT` 와 `REG_DT` 분리 | "측정 시각"과 "DB 저장 시각"은 다름. 나중에 버퍼링/재전송을 하면 차이가 커짐 |
| 클러스터드 = `LOG_ID` | 계속 증가하는 값 → INSERT 가 항상 맨 끝에 붙어 페이지 분할이 거의 없음. 쓰기가 많은 테이블에 유리 |
| 비클러스터드 `(SENSOR_ID, MEASURE_DT)` | 화면 조회 조건이 항상 "센서 + 기간". 순서가 중요: 등호(=) 조건 컬럼을 앞에, 범위 조건을 뒤에 |
| `INCLUDE (TEMP_VALUE, STATUS_CD, ERROR_CD)` | 조회에 필요한 컬럼을 인덱스에 같이 넣어, 테이블 본체를 다시 찾아가지 않게 함 (**커버링 인덱스**). 오류 종류 표시를 추가하면서 ERROR_CD 도 포함 (스크립트가 예전 인덱스를 자동으로 다시 만듦) |
| 제약조건 이름 명시 (`PK_`, `FK_`, `DF_`, `CK_`) | 이름을 안 주면 `DF__TB_TEMP__ERROR__3B75D760` 같은 랜덤 이름이 생겨 나중에 수정 스크립트 작성이 어려움 |

### 4-4. 데이터 보관 (`USP_PURGE_TEMP_LOG`)

5초 저장이면 1년에 약 630만 건. 오래된 데이터를 한 번에 `DELETE` 하면 트랜잭션 로그가 폭증하고 테이블이 오래 잠깁니다. 그래서 **5,000건씩 나눠서 삭제**하는 프로시저를 만들었고, SQL Server Agent 로 매일 새벽 실행하면 됩니다.

### 4-5. C# ↔ DB 코딩 규칙

| 규칙 | 이유 |
|---|---|
| 모든 값은 `SqlParameter` | 문자열을 이어 붙인 SQL 은 **SQL Injection** 에 뚫림 (`' OR 1=1 --`) |
| 파라미터 타입을 컬럼과 정확히 맞춤 (`AddWithValue` 안 씀) | 타입이 다르면 SQL Server 가 컬럼 쪽을 형 변환해서 **인덱스를 못 탐** (예: VARCHAR 컬럼에 NVARCHAR 파라미터) |
| `using` 으로 연결을 매번 열고 닫음 | 실제로는 커넥션 풀이 재사용하므로 비용이 거의 없고, 연결 누수가 원천 차단됨 |
| `OUTPUT INSERTED.ALERT_ID` | INSERT 와 동시에 새 ID 를 받음. `@@IDENTITY` 는 트리거가 있으면 엉뚱한 값 |
| 연결 문자열은 App.config | 서버가 바뀌어도 재컴파일 없이 설정 파일만 수정 |

> **면접 포인트**: "측정 이력 테이블은 쓰기 위주라 증가형 키에 클러스터드 인덱스를 두고, 조회 패턴(설비+기간)에 맞춰 커버링 인덱스를 따로 만들었습니다. 온도는 센서 해상도에 맞춰 DECIMAL(5,1), 센서 오류 값은 NULL 로 구분했고, 경고 이력에는 당시 기준값을 스냅샷으로 저장했습니다. 상태값은 공통코드 테이블로 관리했습니다."

## 5. 직접 해볼 개선 과제 (포트폴리오 확장용)

난이도 순입니다. 하나씩 해 보고 README 에 "개선 이력"으로 쓰면 좋습니다.

1. **비밀번호 변경 화면** + PBKDF2(`Rfc2898DeriveBytes`) 로 해시 교체
2. **엑셀 내보내기** (온도 기록 탭) — 현장에서 가장 많이 요청하는 기능
3. **시간대별 통계** (1시간 평균/최고/최저) — `GROUP BY DATEADD(HOUR, DATEDIFF(HOUR, 0, MEASURE_DT), 0)`
4. **DB 장애 시 로컬 버퍼링** — DB 저장 실패 데이터를 메모리 큐/파일에 모았다가 복구 후 재전송 (MEASURE_DT 와 REG_DT 를 분리한 이유가 여기서 드러남)
5. **다중 센서** — TB_SENSOR 에 여러 대 등록, 센서별 폴링 루프 (DB 구조는 이미 준비됨)
6. **스토어드 프로시저로 전환** — 회사마다 "SQL 은 전부 SP" 규칙인 곳이 많음. 지금 Repository 의 SQL 을 SP 로 옮겨 보기
7. **로그 파일** (NLog/Serilog) — 통신 오류를 파일로 남겨 현장 장애 분석
8. **그리드 정렬 UI 개선** — 지금은 정렬 가능 여부를 손 모양 커서 + 툴팁으로만 알려 줌 (마우스를 올려야 알 수 있음)
   - 방법 A (사무실 PC): 정렬 가능 컬럼은 흐린 회색 ▲▼ 를 처음부터 표시, 정렬 중인 컬럼만 진한 ▲ 또는 ▼ → `CellPainting` 으로 헤더 직접 그리기. 헤더 마우스 오버 시 배경 밝게 하는 효과를 함께 적용
   - 방법 B (현장 터치 PC): 조회 조건 옆에 정렬 콤보박스 (최신순 / 오래된순 / 온도 높은 순 / 경고·오류 먼저) → 정렬을 SQL `ORDER BY` 로 처리해 50,000건 제한에서도 정확하고, 가나다순이 아닌 업무 기준 정렬(공통코드 SORT_NO) 가능. 헤더 정렬은 시간만 남김
   - 참고: 실무 MES 는 DevExpress / Infragistics / FarPoint Spread 같은 상용 그리드에 이 기능들이 기본 내장

## 7. 장비 없이 테스트 — Sig5560Simulator

실제 SIG-5560 과 같은 레지스터 맵으로 응답하는 콘솔 Modbus/TCP 서버입니다. TempMonitor 코드는 그대로, IP 만 `127.0.0.1` 로 연결합니다.

실행: 솔루션 탐색기 → Sig5560Simulator 우클릭 → 디버그 → 새 인스턴스 시작 (포트 인자 생략 시 502)

| 키 | 동작 | 확인할 것 |
|---|---|---|
| ↑ / ↓ | 목표 온도 ±1℃ (서서히 변함) | 차트, 실시간 기록 |
| W / N | 목표 35℃ / 25℃ 정상 복귀 | 경고 → 상승 → 복귀 알림 |
| 1 ~ 4 / 0 | 에러 코드 발생 / 해제 | 센서 오류 표시, DB 에 온도 NULL |
| T | 무응답 모드 | 3초 타임아웃 → 재연결 |
| R | 최저/최고 리셋 | FC05 처리 |

> **면접 포인트**: "장비 없이도 개발할 수 있도록 Modbus 슬레이브 시뮬레이터를 직접 만들어, 센서 단선·통신 무응답처럼 실제 장비로는 재현하기 어려운 예외 상황까지 테스트했습니다."
